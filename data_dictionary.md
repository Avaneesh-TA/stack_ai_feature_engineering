## 1. Business context (inferred)

Inferred from column names and value distributions, **stated as inference, not fact**:

- This is an **e-commerce customer churn** dataset. The unit of analysis is the customer
  (`customer_id`, 1–1500). The prediction target is the binary column `churned` on
  `customers.csv`.
- `transactions.db` holds **row-level order/transaction events** for those customers
  (amount, category, channel, an `is_returned` flag). `transactions_monthly_agg.parquet` is a
  **pre-aggregated customer × calendar-month** extract of the same event stream
  (txn count, total amount, return count).
- The three sources describe the same population at different grains. `customers.csv` is the
  static profile + label; the two transaction sources are the behavioral signal.

⚠ **low-confidence:** the precise business definition of "churn" is not stated in any provided
file; it is inferred from the label's empirical relationship to recency (see §6, "Label
relationship & leakage risk"). That inference is unusually clean but is still an inference.

## 2. As-of date convention

The starter scripts (`scripts/build_training_features.py`, `scripts/score_customer.py`)
default `--as-of` to **2026-08-01**. This is a sensible scoring point because:

- The last row-level transaction in `transactions.db` is `2026-07-31 23:50:29`, so
  2026-08-01 is "the day after the last observed event."
- `customers.csv` `signup_date` runs 2024-02-14 → 2026-07-01 (no signups after the as-of;
  tenure is always positive as of 2026-08-01, min 31 days).

⚠ **This as-of date is in tension with the label.** See §6: the `churned` label appears to be
defined by activity in the trailing ~90 days *ending* at 2026-08-01. Computing behavioral
features "as of 2026-08-01" over a trailing window that overlaps those 90 days risks leaking
the label. The learner must decide in `feature_spec.md` whether to (a) compute features as of
the **start of the churn window** instead (~2026-05-03), or (b) explicitly exclude the churn
window from feature windows. Stage 0 flags this; it does not resolve it.

## 3. Source 1 — `data/customers.csv`

One row per customer. 1500 rows, 5 columns, **no nulls**.

| column | dtype (observed) | nullable (observed) | meaning / values |
|---|---|---|---|
| `customer_id` | int64 | no | Customer key, 1–1500, unique, no duplicates. |
| `signup_date` | datetime (ISO `YYYY-MM-DD`) | no | Account creation date. Range 2024-02-14 → 2026-07-01. |
| `acquisition_channel` | string | no | One of `organic` (609), `paid_search` (431), `referral` (295), `social` (165). |
| `region` | string | no | One of `east` (385), `north` (381), `west` (380), `south` (354). Evenly distributed. |
| `churned` | int64 (0/1) | no | Target label. 202 churned (13.5%), 1298 not churned (86.5%). |

Observed univariate relationships with the label (correlation, **not causation**):

- Churn rate by channel: `organic` 15.3% > `social` 14.5% > `referral` 13.9% > `paid_search` 10.2%.
  ⚠ **low-confidence / counterintuitive:** the common intuition "paid-acquired customers churn
  more" is **contradicted** by this data — `paid_search` has the *lowest* churn. Any rationale
  using acquisition channel must account for this observed direction, not assert the opposite.
- Churn rate by region: `east` 16.4% > `south` 12.7% ≈ `west` 12.4% ≈ `north` 12.3%. Mild;
  `east` is somewhat elevated. ⚠ low-confidence as a churn driver.

## 4. Source 2 — `data/transactions.db` (SQLite, table `transactions`)

Row-level events. 11,742 rows, 6 columns, **no nulls**. SQLite stores `txn_timestamp` as
ISO-8601 text and must be parsed to datetime on load.

| column | SQLite type | pandas dtype after parse | nullable (observed) | meaning / values |
|---|---|---|---|---|
| `customer_id` | INTEGER | int64 | no | FK to `customers.csv`. Range 2–1500 (customer 1 never transacts). |
| `txn_timestamp` | TEXT | datetime | no | Event timestamp, ISO-8601 with fractional seconds. Range 2024-02-29 → 2026-07-31. |
| `category` | TEXT | string | no | One of `home`(2008), `grocery`(1979), `sports`(1969), `beauty`(1958), `apparel`(1917), `electronics`(1911). Evenly distributed. |
| `channel` | TEXT | string | no | One of `web`(5278), `mobile_app`(4146), `store`(2318). |
| `amount` | REAL | float64 | no | Transaction dollar amount. Min $3.00, max $1684.21, mean $49.72, median $33.82. **Right-skewed** (mean > median; 75th pct $61.39 vs max $1684). All amounts > 0. |
| `is_returned` | INTEGER | int64 (0/1) | no | Return flag. 591 returned (5.0%), 11,151 not. |

Data-quality notes for this source:

- **Returns are stored as positive `amount`s, not negatives** (min returned-amount = $3.00,
  none ≤ 0). A return is signaled only by `is_returned=1`. Consequence: a naive `SUM(amount)`
  "spend" feature **includes** returned-txn dollars. The spec must decide whether "spend"
  means gross (sum of all `amount`) or net (sum of `amount` where `is_returned=0`); the two
  differ by exactly the returned-txn total.
- **81 customers have zero rows** in this table (customer_ids with no transactions). See §6.
- Row counts per customer: min 1, median 7, max 32 (among the 1419 customers who transact).

## 5. Source 3 — `data/transactions_monthly_agg.parquet`

Pre-aggregated customer × calendar-month. 8,086 rows, 5 columns, **no nulls**. `txn_month`
is stored as a first-of-month datetime.

| column | dtype (observed) | nullable (observed) | meaning / values |
|---|---|---|---|
| `customer_id` | int64 | no | FK to `customers.csv`. 1,409 distinct customers (10 fewer than the DB; see §6). |
| `txn_month` | datetime (first-of-month) | no | Calendar month. Range 2024-02-01 → 2026-07-01. |
| `txn_count` | int64 | no | Number of transactions in that customer-month. Min 1, max 6, median 1. |
| `total_amount` | float64 | no | Sum of `amount` for that customer-month. Min $3.00, max $1753.23, median $48.32. Right-skewed. |
| `return_count` | int64 | no | Number of returned txns in that customer-month. Min 0, max 3, median 0. |

Grain: one row per (customer, calendar month) **in which the customer had ≥1 transaction**.
Months with zero activity have **no row** (not a zero row) — any feature from this source must
reindex against the full customer list and fill the missing months explicitly.

## 6. Data-quality realities actually detected by inspection

These were verified against the data, not assumed.

### 6.1 Customers with zero transaction activity exist — and 100% of them are churned

- **81 customers have zero rows in `transactions.db`** (customer_ids with no events).
- **91 customers have zero rows in `transactions_monthly_agg`** (10 more — see 6.2).
- The 81 zero-`transactions.db` customers are a **strict subset** of the 91 zero-monthly
  customers, and the 81 are all absent from the monthly aggregate too.
- **All 81 zero-transaction customers have `churned = 1`** (100%). Overall churn rate is 13.5%,
  and churn rate among customers *with* ≥1 transaction is 8.5%. This is not a soft correlation
  — it is a definitional-looking link. See 6.4.

### 6.2 The monthly aggregate is ETL-lagged in the latest month (2026-07)

A direct row-level-vs-aggregate reconciliation found **212 customer-month rows where the
`transactions.db`-derived monthly totals disagree with `transactions_monthly_agg`** (out of
8,188 matched rows). Key facts:

- **Every disagreement is in the `2026-07` month** (zero disagreements in any earlier month).
  The monthly aggregate's reliable, complete data runs through **2026-06**; 2026-07 is partial.
- The aggregate **never has a row the row-level DB lacks** (the disagreement is one-directional:
  the DB always has ≥ what the aggregate shows).
- Two failure modes within 2026-07:
  - **102 cases:** the aggregate month is **entirely missing** (DB has July transactions for
    the customer, the aggregate has no July row at all). This accounts for the 10 customers
    present in the DB but absent from the monthly aggregate entirely — all 10 transact *only*
    in July 2026.
  - **110 cases:** the aggregate **undercounts** the month (both have a July row, but the
    aggregate's `txn_count`/`total_amount` are lower than the DB-derived values — e.g.
    customer 2: DB shows 2 July txns / $136.62, aggregate shows 1 / $3.00).

**Implication for the build:** any feature whose window includes July 2026 **cannot** trust the
monthly aggregate and must use the row-level `transactions.db`. Any feature that can be
defined on complete calendar months through 2026-06 may use either source. This is the core
multi-source judgment the spec must make per feature.

### 6.3 Returns are positive amounts; spend sums include returned dollars

See §4. `SUM(amount)` is gross spend; net spend requires `WHERE is_returned = 0`.

### 6.4 Label relationship & leakage risk (the most important finding)

Empirically, `days_since_last_txn` computed **as of 2026-08-01** is a **perfect separator** of
the label:

| days since last txn (as of 2026-08-01) | customers | churn rate |
|---|---|---|
| ≤ 30 days | 787 | 0.0% |
| 31–90 days | 511 | 0.0% |
| 91–180 days | 104 | 100.0% |
| 181–365 days | 17 | 100.0% |
| no transaction ever | 81 | 100.0% |

All non-churned customers transacted within the last 90 days (last txn in 2026-05/06/07); all
churned customers' last transaction is ≥91 days ago or never (last txn 2025-12 → 2026-04,
peaking 2026-04). **There is zero overlap at the 90-day boundary.**

Inference: `churned` is effectively defined as "no transaction in the trailing ~90 days ending
2026-08-01" (the churn/performance window is roughly 2026-05-03 → 2026-08-01). ⚠ low-confidence
on the exact threshold (90 days vs a nearby value) but high-confidence on the *existence* of a
clean threshold.

**Leakage consequence — the learner must address this in `feature_spec.md`:**

- Any feature computed **as of 2026-08-01** over a **trailing window that overlaps the churn
  window** (the last ~90 days) reproduces the label rather than predicting it:
  - `days_since_last_txn` (as of 2026-08-01) **is the label**, by construction.
  - `txn_count_last_90d` (as of 2026-08-01) is 0 for every churned customer and >0 for every
    non-churned customer — a perfect separator, i.e. pure leakage.
  - Even `txn_count_last_180d` / `spend_last_180d` partially overlap the churn window.
- The clean way to avoid this is to compute behavioral features **as of the *start* of the
  churn window** (~2026-05-03), using only data at or before that point, so features describe
  pre-window behavior. The alternative is to keep as-of 2026-08-01 but define features over
  windows that end before the churn window begins. Either way, short-window recency/frequency
  features are **leakage** if naively computed as of 2026-08-01, and the spec must say so
  rather than present them as ordinary predictive features.
- Features that capture **behavior relative to the customer's own baseline** (a trend, a
  drop from their own historical norm) carry signal that is not merely a restatement of the
  label and are the more defensible families here.

## 7. Time dimensions and source alignment

| source | timestamp column | grain | reliable through |
|---|---|---|---|
| `customers.csv` | `signup_date` (date) | one row per customer (static) | all of it (no time-varying component) |
| `transactions.db` | `txn_timestamp` (datetime, sub-second) | one row per transaction event | 2026-07-31 (last event) |
| `transactions_monthly_agg.parquet` | `txn_month` (first-of-month) | one row per (customer, calendar month) | **2026-06** (2026-07 is partial/missing — see 6.2) |

Sources can disagree at the edges: §6.2 documents a real, verifiable, one-directional gap in
2026-07. Earlier months reconcile exactly. The two transaction sources describe the same
event stream at different grains; the row-level table is always the source of truth and the
aggregate is a convenience that lags the current month.

**No first-transaction-before-signup ordering bug** was found (0 cases), so
`signup_date → first_transaction` is a valid latent period if a feature wants it. Tenure as of
2026-08-01 ranges 31–899 days (no negative tenures — no signups after the as-of).

# Part 2 — Candidate-feature proposal

> Best-effort proposal to give the learner something concrete to react to. Each feature has a
> name, source(s), computation, an explicit **zero-activity default**, and a rationale. This
> is **not** `feature_spec.md` — the learner corrects this into the spec (see `skill.md`
> Stage 0). Per-feature leakage notes are inline because of §6.4.

## How to read the leakage flags

- 🚨 **LEAKAGE** if computed as of 2026-08-01 over a trailing window overlapping the churn
  window (last ~90d). The honest version computes the feature as of ~2026-05-03 (churn-window
  start) or over a window ending before the churn window.
- ⚠ **PARTIAL overlap** with the churn window depending on the window length.
- ✅ Not a restatement of the label (pre-window or static signal).

## A. Customer-profile features (source: `customers.csv`) — ✅ no leakage

### F1. `tenure_days`
- **Source:** `customers.csv: signup_date`
- **Computation:** `(as_of - signup_date).days`
- **Zero-activity default:** N/A (every customer has a `signup_date`); always defined.
- **Rationale:** newer customers have not yet formed a purchasing habit and churn at higher
  rates; this is distinct from inactivity — a new customer can be highly active and still be
  at structural churn risk because the habit is unproven. ✅
- **Leakage:** none (signup is before any churn window).

### F2. `acquisition_channel` (categorical)
- **Source:** `customers.csv: acquisition_channel`
- **Computation:** pass through as categorical (encode downstream).
- **Zero-activity default:** N/A.
- **Rationale:** ⚠ **low-confidence / data-contradicted.** The naive hypothesis "paid-acquired
  customers churn more" is **false in this data** (`paid_search` has the *lowest* churn, 10.2%).
  A defensible rationale is weaker: acquisition channel captures cohort/intent differences
  that *may* correlate with retention through some mechanism (e.g. promotion dependence), but
  the observed direction should not be asserted blindly. The learner should decide whether
  this feature earns a place.
- **Leakage:** none.

### F3. `region` (categorical)
- **Source:** `customers.csv: region`
- **Computation:** pass through as categorical.
- **Zero-activity default:** N/A.
- **Rationale:** ⚠ **low-confidence.** Regional differences (e.g. `east` at 16.4% churn vs
  ~12.3% elsewhere) *could* reflect fulfillment quality or local competition, but the effect is
  mild and the mechanism is guessed. Plausible but thin.
- **Leakage:** none.

## B. Recency / frequency features (source: `transactions.db`) — 🚨 leakage if as_of=2026-08-01

### F4. `days_since_last_txn`
- **Source:** `transactions.db: txn_timestamp` (row-level — the monthly aggregate cannot
  express an exact recency window)
- **Computation:** `(as_of - max(txn_timestamp)).days` for customers with ≥1 txn.
- **Zero-activity default:** a large sentinel (e.g. tenure_days, or a defined "no activity"
  constant) — **never NaN**. The spec must name the exact default.
- **Rationale:** longer time since last activity is a direct churn signal. 🚨 **BUT in this
  dataset, as of 2026-08-01 this feature is a perfect separator of the label (§6.4) — it is
  the label's definition, not a predictor. As a *candidate* it is the canonical recency
  feature; as *built feature* it leaks unless `as_of` is moved to the churn-window start.
- **Leakage:** 🚨 severe if `as_of = 2026-08-01`.

### F5. `txn_count_last_Nd` (windowed frequency)
- **Source:** `transactions.db: txn_timestamp` for short windows (the monthly aggregate can't
  align a rolling N-day window to calendar months); `transactions_monthly_agg: txn_count` is
  fine for calendar-month-aligned longer windows.
- **Computation:** count of `txn_timestamp` in `(as_of - N days, as_of]`.
- **Zero-activity default:** `0` (an integer count — never NaN).
- **Rationale:** transaction frequency in a window is a core engagement signal. 🚨 For
  N ≤ 90 and `as_of = 2026-08-01`, this is 0 for all churned customers — leakage (§6.4). For
  larger N it partially overlaps the churn window.
- **Leakage:** 🚨 for N ≤ 90 at `as_of = 2026-08-01`; ⚠ partial for larger N.

## C. Monetary features — ⚠ partial overlap depending on window

### F6. `avg_monthly_spend` (last 12 complete months)
- **Source:** `transactions_monthly_agg: total_amount` (calendar-month granularity is fine for
  a monthly average; **must exclude the partial 2026-07**, §6.2)
- **Computation:** mean of `total_amount` over the last 12 *complete* customer-months
  (i.e. through 2026-06), reindexed so missing months count as 0 or are excluded per spec.
- **Zero-activity default:** `0.0` — never NaN.
- **Rationale:** lower spend level is associated with churn but is confounded with engagement
  breadth; more useful as a baseline for a trajectory feature (F8) than as a standalone. Note
  the right-skew (§4): a mean is pulled by a few large spenders; the spec may prefer a
  median or a clipped/transformed value.
- **Leakage:** ⚠ if the 12-month window extends into the churn window; compute through
  2026-06 (before the churn window) to be safe. Decide net vs gross (§6.3).

### F7. `spend_last_Nd`
- **Source:** `transactions.db: amount` for precise N-day windows (aggregate can't align
  rolling N-day); `transactions_monthly_agg: total_amount` for calendar-month windows.
- **Computation:** `SUM(amount)` in `(as_of - N days, as_of]` (gross) or
  `SUM(amount WHERE is_returned=0)` (net) — spec must pick.
- **Zero-activity default:** `0.0`.
- **Rationale:** recent spend magnitude; right-skewed so consider log/clip.
- **Leakage:** ⚠ same window-overlap caveat as F5.

## D. Engagement-consistency feature (source: `transactions_monthly_agg`) — ✅ good

### F8. `active_months_last_12m`
- **Source:** `transactions_monthly_agg: txn_month` (naturally suited to the aggregate; the
  row-level table could also derive it but the aggregate is the convenient source)
- **Computation:** count of distinct `txn_month` values in the last 12 complete months
  (through 2026-06) where the customer had ≥1 txn. Reindex over the full customer base.
- **Zero-activity default:** `0` — never NaN.
- **Rationale:** breadth of activity over a longer window captures engagement consistency —
  a customer active in many of the last 12 months has a stable habit. This is **not** a
  restatement of the label: a churned customer (last txn 2026-04) can still have had 9 active
  months in the trailing year, and a non-churned customer can have had only 3. It separates
  "always-sparse but present" from "was-broadly-engaged-then-lapsed."
- **Leakage:** ✅ if computed through 2026-06 (excludes the churn window). ⚠ if the 12-month
  window reaches into the churn window.

## E. Trend / trajectory feature — ✅ the strongest defensible signal

### F9. `spend_trajectory` (recent vs own baseline)
- **Source:** `transactions_monthly_agg: total_amount` (calendar-month granularity is fine for
  a month-ratio); or `transactions.db` for a rolling-window ratio. Either works; the aggregate
  is cheaper but must exclude 2026-07.
- **Computation:** ratio (or difference) of recent mean monthly spend to the customer's own
  prior baseline monthly spend — e.g. mean of the 3 most recent *complete* months ÷ mean of
  the prior 3 complete months, computed **before the churn window**. Define a floor to avoid
  divide-by-zero.
- **Zero-activity default:** `1.0` (no change) or `0.0` per spec — never NaN; handle
  zero-baseline explicitly.
- **Rationale:** a decline in spend **relative to the customer's own baseline** signals
  disengagement, **distinct from a customer who has always spent little** (the canonical
  "real vs filler" rationale: it names a behavior — a drop from their own norm — and
  distinguishes it from the confound of a perpetually-low spender). This is the most defensible
  family in this dataset because it is not a restatement of the label.
- **Leakage:** ✅ if the "recent" period ends before the churn window; ⚠ otherwise.

## F. Return / quality signal — ✅ if window is pre-churn

### F10. `return_rate` (windowed)
- **Source:** `transactions.db: is_returned` (count-based; the monthly aggregate has
  `return_count` and `txn_count`, so a calendar-month version is also available)
- **Computation:** `SUM(is_returned) / COUNT(*)` over a window **ending before the churn
  window** (otherwise a churned customer trivially has 0 returns in the churn window = leakage
  by another name).
- **Zero-activity default:** `0.0` — never NaN.
- **Rationale:** a rising share of returns signals unmet expectations / dissatisfaction that
  can precede churn, **distinct from low spend** — a customer can spend normally and still be
  trending toward churn if their return share is climbing. Overall return rate is ~5% with
  modest category variation (4.5%–5.7%).
- **Leakage:** ✅ if window ends before churn window; 🚨 if it overlaps (0 returns for
  churned customers in the churn window).

## Versioning-exercise candidates (suggestion only — the learner decides)

Stage 0 can suggest, not decide. Features above that **naturally take a tunable parameter**
and so are good candidates for the spec's required "≥2 distinct features, each ≥2 versions"
versioning exercise:

- **F5 `txn_count_last_Nd`** — parameter `window_days` (e.g. 90 vs 180 vs 365). Different
  windows give materially different values and have different leakage overlap, so a version
  bump here is real, not cosmetic.
- **F9 `spend_trajectory`** — parameter `recent_window_months` / `baseline_window_months`
  (e.g. 3-vs-3 vs 6-vs-6), or a `floor`/`multiplier` on the ratio.
- **F6 `avg_monthly_spend`** — parameter `window_months` (6 vs 12) or a clip threshold.

The spec must state, per versioned feature, the parameter, the value at **every** version,
and a **business reason** each new version's value changed (not "just testing a different
number"). Stage 0 does not invent those reasons.

## Deliberate omissions (so they are not assumed to be oversights)

- **`category` / `channel` diversity features** (e.g. number of distinct categories
  purchased) are plausible engagement-breadth signals but are not proposed here — they add
  complexity without a clearly stronger rationale than `active_months_last_12m` (F8), and the
  spec's versioning floor is already covered. The learner may add one if desired.
- **A standalone `days_since_last_txn` (F4) used as a predictor** is proposed as a candidate
  only to flag its leakage; a spec that ships it unmodified at `as_of = 2026-08-01` would be
  shipping the label. This is a deliberate warning, not an endorsement.
